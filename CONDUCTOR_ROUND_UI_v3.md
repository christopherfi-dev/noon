# Conductor Round UI (v3) — What the Student Sees, the Report, Progress Codes

**This file replaces `CONDUCTOR_ROUND_UI.md` and `CONDUCTOR_ROUND_UI_v2.md`.** Place it in the repository root
and read it before acting. Record this round as a separate interval in
`BUILD_LOG.md`. Earlier conductor files still govern.

**Scope.**
- U1–U9 change presentation and learner-facing wording only.
- U10 and U11 add one engine feature: a progress code that carries a
  learner's results into a later session, and a safe upgrade path for it.
- Evidence rules, checkers and model handling are unchanged. Every existing
  behavioural test keeps its assertions. Tests that check exact wording
  change only where U1–U9 change that wording (for example "That is not
  correct." becomes "Not yet.").
- The engine must still run on PHP 8.0.
- Every sentence in the report is generated by code from recorded evidence. No
  model-written text appears in the report.

**Offline only:** no live run, no key, nothing deployed.

## 1. Changes

**U1. Show the problem the feedback is about.** When feedback refers to an
earlier answer, show that problem and the learner's answer with it. For
example, "On 8(x + 5) = 64 you answered 13." then the observation. For a multiple-choice item,
write "you chose A and C". Feedback must
never mention numbers that appear only in a problem the learner can no longer
see.

Test: in the B1 journey, the feedback block that precedes the first guided
problem contains the missed problem and the learner's answer.

**U2. The session report.** This is shown at the end of a session and is the
content of the download in U9.
- **For the learner.** Four headings, in this order and with these exact words.
  Plain language, skill titles only, no IDs:
  1. **What you did well:** goals met this session and correct answers given
     without help.
  2. **Where you had trouble:** skills with wrong answers or where help was
     used, plus observed mistake patterns written as observations, for
     example "Several times you multiplied only the x by the number outside
     the parentheses."
  3. **What we worked on:** practice with help, and the route taken, for
     example "We went back to the distributive property, then returned to
     solving equations with parentheses."
  4. **What to work on next time:** unmet goals and unresolved gaps. A gap
     outside the beta reads "Practise with your teacher: <skill title> (not
     in this tutor yet)."
- **"Details for teachers":** the full record, collapsed on screen and expanded
  in the download. It has no raw codes such as `AVAILABLE_SCORED`,
  `all_of edge` or bare `Q07`. Skill IDs may appear in brackets after titles.
  Replace these terms with plain words in both parts:
  - declared prerequisite
  - descent / descended
  - implicated
  - branch
  - transfer variant
  - retention claim
  - faded support
  - coverage
- **Empty headings.** Each heading has a fixed line for when it has nothing
  to report:
  - What you did well: "No goals were met in this session yet."
  - Where you had trouble: "No trouble spots were recorded in this session."
  - What we worked on: "This session had no practice with help."
  - What to work on next time: "You met every goal available in this tutor so
    far. Ask your teacher what comes next."

  Never invent praise or problems to fill a heading.
- Remove duplicate lines.
- Under 600px the per-skill table becomes stacked cards. No cell may wrap a
  word letter by letter.
- Results from an earlier session (U10) appear under their own label, "From
  earlier sessions", with the date. They are never merged into this session's
  goals.

Extend the summary wording test to the new terms. Every truth rule from rounds
5 and 5.1 applies to both parts.

**U3. Multiple-choice items.**
- Each checkbox label is the full option text, for example
  "A) Multiply only the x by 9: 9x − 2 = −81". Do not repeat the options in the
  question stem.
- Every equation or expression is wrapped so it never breaks across lines
  (`white-space: nowrap` on a math span). The surrounding sentence may wrap.
- The question stem is normal weight. Only the item's main expression may be
  emphasised.

**U4. Remove the "Working (optional)" box.** Nothing reads it, and learners
would reasonably assume the tutor does. The API keeps accepting an empty
`working` field so nothing else changes. Update the privacy notice and the
summary to stop mentioning working. Record this in the capability matrix as
"removed until a reader exists".

**U5. Fewer buttons.**
- **Independent items:** Submit, "I'm stuck", Skip (Skip only where the
  engine allows it). "I'm stuck" opens three choices:
  - "Give me a hint" (hint action)
  - "Explain the idea" (explanation action)
  - "I haven't learned this yet" (not-learned action)
- **Guided steps:** Submit and "I'm stuck", which opens:
  - "Give me a hint"
  - "Explain the idea"
  - "I don't know"

  Keep every action that exists today; this change only regroups them.
- Each choice sends the same action as today's button, and the engine
  behaviour is unchanged. Typed stuck entries (round 5) still work. The menu works by keyboard, uses
`aria-expanded`, and returns focus to the answer field when closed.

**U6. One notice per fact.** The guided-work notice appears once, as the tag
on the item. Remove the duplicate from the header text.

**U7. Visible goal progress.** Show the dots only in modes where answers
count toward a streak: target assessment, independent check and return to
target. Never show them on a diagnostic probe or a single prerequisite check.
The count and the label come from the criterion the engine is tracking for
that skill. Show three dots that fill
for each correct answer in a row without help. Next to them, a short label such
as "2 of 3 in a row" and the kinds of item still needed, for example "still
needed: a step choice". When the streak resets, the dots empty. Screen readers
get the same information as text.

**U8. Correct and not-yet feedback look different.**
- Correct: a green-tinted block with a check icon and the word "Correct."
- Incorrect: a neutral block with the words "Not yet." This replaces "That is
  not correct." everywhere, matching the guided steps.
- Colour is never the only signal: an icon and words always accompany it.
- Both colours meet WCAG AA contrast in light and dark mode.

**U9. Download to share with a teacher.**
- **"Download report":** saves one self-contained `.html` file named
  `algebra-report-YYYY-MM-DD.html`, with inline CSS, no scripts and no
  external requests. It contains the four learner headings, the teacher
  details expanded, the date and the progress code (U10).
- **"Print or save as PDF":** opens the browser print dialog, with a print
  stylesheet that prints the same content cleanly.
- The JSON download moves inside "Details for teachers".

**U10. Progress code, to continue next time.**

The goal: a learner types one short code and continues where they left off,
even if they closed the tab without ending the session.

- **Created at the first answer.** The code and its record are created when the
  first answer of a session is recorded, not at session end. From then on the
  code is visible on screen, under a "Your code" label in the header area,
  with the line "Write this down or download your report to continue next
  time." It also appears in the report and the download.
- **Code format.** 12 characters from an alphabet without 0, O, 1, I or L,
  shown in groups of four (for example `K7QM-4XRT-9WPC`). It has at least 60
  bits of randomness. Check it is unique when it is created.
- **Entering a code.** Input is accepted in any case, with or without spaces or
  dashes.
- **Updated every turn.** The record is updated in the same database
  transaction as each recorded answer. Closing the tab at any point loses
  nothing that was answered.
- **What the record holds.**
  - Per skill: status (goal met / needed help / unresolved / not in the beta),
    the date, and the observed mistake-pattern codes.
  - `route_target`: the skill the learner set out to master.
  - `next_skill`: the deepest unmet skill on the current route. That is the
    skill being repaired if the session stopped mid-repair, otherwise the
    route target.

  Nothing else: no answers, no names, no IP address. The record is cumulative
  across sessions.
- **Storage.**
  - Store only the sha256 of the code, never the code itself, and compare in
    constant time.
  - Keep the record for `progress_retention_days` (default 90) after its last
    use. The existing cleanup deletes expired records.
  - If a server's existing `config.php` lacks this key, the default applies.
- **Continuing.** The welcome screen has a "Continue with a progress code"
  field. A valid code shows a "Welcome back" card summarising the four
  headings from last time, and a Start button.
  - **If the code's session is still live:** Start continues that session
    exactly where it stopped.
  - **Otherwise:** Start begins a new session targeting `next_skill`. When its
    goal is met and `next_skill` differs from `route_target`, show "Next:
    <route target title>" using the existing change-topic path.
  - **If every goal on the route is met:** say so, and offer the beta skill
    list.
- **One device at a time.** A code links to at most one live session. Entering
  it on another device takes over. The old session then shows "This progress
  continued on another device." and accepts no more answers. Use the existing
  revision checks so no update is lost.
- **Evidence rule.** A goal met in an earlier session never counts as met in
  the new session. The report lists it under "From earlier sessions" with its
  date.
- **Bad codes.** An unknown, mistyped or expired code gets one generic message
  ("That code wasn't found. Check it, or start fresh.") that never reveals
  whether a code exists. Limit lookups to 10 failures per hour per session.
- **Start over.** "Start over" begins a fresh session with no code and leaves
  any existing record untouched.
- **Forget.** "Forget this session" also deletes the progress record linked to
  the session, and says so.
- **Privacy notice.** Add these two sentences:
  - "Progress codes keep skill results only, for up to 90 days after last
    use."
  - "Anyone with your code or your downloaded report can continue your
    progress."

**U11. Upgrading a live server without breaking it.** The current version will
already be running on the VPS, with sessions in its database, when this update
lands.
- Add the progress table through the existing migration mechanism. Migration
  runs automatically and is safe to run twice. It never deletes or rewrites
  existing data.
- Test it: create a database with the previous release (commit `a1f9e16`), put
  a live session in it, apply this release, and confirm the session continues
  and a code is created at its next answer.
- Neither bundle may contain `config.php` or any file inside `var/`, so
  unpacking over a live install can never overwrite the server's config or
  its database.
- Add an "Updating an existing install" section to `DEPLOYMENT_VPS.md`:
  replace the code folders, keep `config.php` and `var/`, then run the
  preflight.
